# What companies ship today — KV-cache memory reduction & reuse in production

**Compiled:** 2026-10-04. Every fact below was opened live in this session (official docs, blogs, model cards, config.json files, GitHub repos, arXiv papers). Numbers are quoted as the source states them; anything not independently confirmed is explicitly marked **UNVERIFIED**. No fact is filled from training memory. Citation format: inline `[n]` keyed to the numbered source list at the end.

---

## Top 10 findings

1. **DeepSeek's MLA is the most aggressive *architectural* KV-cache cut with hard numbers on record.** The DeepSeek-V2 paper's headline claim is "reduces the KV cache by 93.3%" vs. DeepSeek‑67B (MHA); a controlled ablation in the same paper (Table 9, matched architecture) measures KV cache per token at **15.6K / 110.6K ≈ 14%** of MHA for a small MoE and **34.6K / 860.2K ≈ 4%** for a large MoE — i.e., MLA's own table shows the saving gets *more* extreme at larger scale. MLA is also the explicit enabler of DeepSeek's disk-based context caching ("made possible by the MLA architecture... enabling efficient storage on low-cost disks") [17,18].
2. **Character.AI's 2024 production stack is the most complete public "stack everything" disclosure**: MQA (reduces KV cache **8× vs. GQA**, not vs. plain MHA — a common misreading), 1-in-6-layers global attention with a 1024-token local window, cross-layer KV tying (**2–3× further**), and native int8 training, combining to "**reduce KV cache size by more than 20X**" — plus a separately-reported **95% "cache rate"** from sticky-session prefix caching. No 2025/2026 follow-up post with updated numbers was found [38–40].
3. **OpenAI's open-weight gpt-oss models are a rare case of a frontier-adjacent lab shipping the exact mechanism in code, not just marketing.** `config.json` shows `sliding_window=128` and a `layer_types` array alternating `sliding_attention`/`full_attention` across all 36 layers, with **GQA 64:8** (8 query heads per KV head). The "learned attention sinks" are **not** a config field — they are a per-head `nn.Parameter` (`self.sinks`, one scalar per of 64 heads, bf16) folded directly into the flash-attention softmax denominator, confirmed in `gpt_oss/torch/model.py` and `gpt_oss/triton/attention.py` ("FlashAttention w/support for learned sinks and banded attention") [1,2].
4. **Apple ships cross-block KV-cache sharing in a real production, on-device model**, not just a paper: the ~3B on-device Apple Intelligence model is split into two blocks at a **5:3 depth ratio**, and block 2 fully reuses ("directly shared") the KV cache from block 1's final layer — an exact, disclosed **37.5% KV-cache memory reduction** plus improved time-to-first-token [27].
5. **Industry convergence on ~3:1 linear-to-full-attention hybrid ratios — but with an open counter-example.** Kimi Linear (Moonshot, Nov 2025) and Qwen3-Next → Qwen3.5/3.6/3.8 (Alibaba, Sept 2025–Aug 2026) independently land on **3:1** (confirmed via ablation + shipped `config.json`), with Kimi Linear reporting **up to 75% KV-cache reduction** and up to **6.3× faster decoding** at 1M tokens. But MiniMax's 2026 **M2** model *reversed* MiniMax-01's 7:1 lightning-attention hybrid back to **pure full attention + GQA**, with MiniMax's own blog explaining the hybrid "had clear deficits in complex, multi-hop reasoning tasks" at scale [19–24].
6. **Context-caching price discounts have converged near 90% off** across OpenAI (up to 95% for its newest tier), Anthropic (90%, 95% for Opus 5.5) and Google Gemini (90%) — but DeepSeek's disk-based cache goes further: for `deepseek-flash`, off-peak cache-hit price is **$0.003/M tokens vs. $0.15/M miss (50×)** [3,8,12,18].
7. **No production inference stack defaults to lossy token eviction (H2O/SnapKV-style).** NVIDIA's own **kvpress** implements ~25 scoring/eviction methods (SnapKV, StreamingLLM, TOVA, PyramidKV, AdaKV, etc.) but explicitly does **not** implement H2O, and its README self-describes the project as built to "**simplify the development of new methods for researchers and developers**" on top of 🤗 Transformers — a full-text grep found **zero** mentions of vLLM or TensorRT-LLM integration [34].
8. **DeepSeek Sparse Attention (DSA) is a *compute* saving, not a *memory* saving — and it is not "eviction."** DSA's lightning indexer selects the **top-k=2048** tokens per query for attention, cutting complexity from **O(L²) to O(Lk)** — but the full KV cache for all prior tokens is still retained in memory for the indexer to score; nothing is permanently discarded [17].
9. **NVIDIA's newest NVFP4 KV-cache format halves memory versus already-compressed FP8** ("cuts KV cache memory footprint by up to 50%... <1% accuracy loss... up to 3x better TTFT"), and a newer "cold-page NVFP4" scheme stores cold/offloaded blocks in NVFP4 while GPU-resident cache stays at native precision — quantization gains stack on top of architectural and offloading gains in the same production stack [31].
10. **vLLM's own blog documents a real FP8 KV-cache failure mode and fix** — on Hopper, 128K-context needle-in-a-haystack accuracy fell from **91% (BF16) to 13%** with naive FP8 KV cache before a "two-level accumulation" fix restored it to **89%** — concrete, citable evidence that KV-cache quantization is not a free lunch without numerically careful implementation [45].

## Per-company / per-project findings

### OpenAI

**Prompt caching** — current docs at `developers.openai.com/api/docs/guides/prompt-caching` (redirected live from `platform.openai.com/docs/guides/prompt-caching`), accessed 2026-10-04 [3]; original Oct 1, 2024 announcement [4]; Nov 2025 GPT-5.1 update [5]; Sept 22, 2026 "Better prompt caching for GPT-6" update [6].

- **What's cached**: KV tensors (not raw tokens) for the model's full rendered context — instructions, developer messages, tool definitions, conversation history. Quote: *"The prompt cache stores key-value (KV) tensors, not the tokens themselves."* [3]
- **Trigger**: automatic by default. For GPT-5.6+, both implicit (auto breakpoint) and explicit (`prompt_cache_options.mode:"explicit"`, up to 4 breakpoints/request) modes exist; earlier models are implicit-only [3].
- **Minimum threshold**: **1,024 tokens** for GPT-5.6+ (earlier models: varies with tools/images/schemas) [3]. At original 2024 launch: *"prompts longer than 1,024 tokens... increasing in 128-token increments"* [4].
- **Discount (current, GPT-5.6+)**: cache **write** = **1.25×** uncached rate; cache **read** = **0.1×** (90% off) standard, **0.05×** (95% off) for `gpt-6.1-sol`. Worked example quoted: *"writing a prefix once and fully reusing it once costs 1.35× its ordinary input cost, compared with 2× for processing it twice without caching"* [3,6].
- **Discount evolution (exact, dated)**: 50% flat at Oct 2024 launch (e.g., `gpt-4o-2024-08-06`: $2.50 uncached / $1.25 cached) [4] → by Nov 2025 (GPT-5.1) *"cached input tokens 90% cheaper than uncached tokens, and no additional charge for cache writes or storage"* [5] → current (post-GPT-6) docs introduce the new 1.25× write charge and up to 95% read discount [3,6]. **Exact date of the 50%→90% transition is UNVERIFIED** — not found as a single dated announcement.
- **TTL**: GPT-5.6+: `prompt_cache_options.ttl`, only supported value `"30m"` (default) [3]. Earlier models: `prompt_cache_retention` = `"in_memory"` (*"5 to 10 minutes... up to one hour"*) or `"24h"` (*"around 30 minutes... up to 24 hours"*, opt-in since GPT-5.1, Nov 2025) [3,5]. Original 2024 launch: *"typically cleared after 5-10 minutes of inactivity... always removed within one hour"* [4].
- **Cache is machine-local**, not shared across orgs/regions; *"traffic above 15 requests per minute can lead to overflow routing"* [3].
- **New (Sept 2026) tooling**: Prompt Caching Dashboard, a diagnostics API returning structured cache-miss reasons (e.g. `{"type": "cache_miss", "reason": "tools_changed", ...}`), `configuration_update` to change reasoning effort without invalidating the cache, and cache prewarming [6].

**gpt-oss architecture** — `config.json` fetched directly from `huggingface.co/openai/gpt-oss-120b` [1]; code from `github.com/openai/gpt-oss` [2]; official blog [7].

- `sliding_window: 128`; `layer_types`: 36-entry array alternating `"sliding_attention"`/`"full_attention"` (even layers = sliding, odd = full) [1].
- `num_attention_heads: 64`, `num_key_value_heads: 8` → **GQA ratio 8:1** [1]. Blog confirms: *"grouped multi-query attention, with a group size of 8"* [7].
- `rope_scaling`: YaRN, factor 32.0, `rope_theta: 150000`; `max_position_embeddings: 131072` (128K) [1].
- **No "sink" field exists in config.json** (full key enumeration performed) [1]. Attention sinks are implemented as code: `openai/gpt-oss:gpt_oss/torch/model.py:187-190` — `self.sinks = torch.nn.Parameter(torch.empty(config.num_attention_heads, ..., dtype=torch.bfloat16))`, folded into softmax via `QK = torch.cat([QK, S], dim=-1)` then softmax, dropping the sink column after. `gpt_oss/triton/attention.py` docstring: *"FlashAttention w/support for learned sinks and banded attention... extended to support banded attention and learned attention sinks."* [2]
- Official blog prose: *"The models use alternating dense and locally banded sparse attention patterns, similar to GPT‑3... grouped multi-query attention, with a group size of 8... RoPE... context lengths of up to 128k."* The term **"attention sink" does not appear in the blog text itself** — only in the GitHub source code [2,7]. gpt-oss-120b: 36 layers, 117B total/5.1B active params, 128 experts/4 active; gpt-oss-20b: 24 layers, 21B total/3.6B active, 32 experts/4 active [7].
- **UNVERIFIED**: the arXiv model-card (2508.10925) architecture-section prose could not be fetched as readable text this session (only metadata/author list resolved); a third-party paraphrase exists but was not independently confirmed [1,2].

### Anthropic

Source: current docs at `platform.claude.com/docs/en/build-with-claude/prompt-caching` (redirected from `docs.anthropic.com`, consolidated under the "Claude Platform" domain as of Nov 19, 2025–Jan 12, 2026) [8]; pricing [9]; original Aug 14, 2024 launch post [10]; May 22, 2025 1-hour TTL launch [11]; Sept 23, 2026 release notes [12].

- **TTL options**: default **5-minute** lifetime (refreshed free on each use); optional **1-hour** TTL at extra cost, launched May 22, 2025 alongside Claude Opus 4/Sonnet 4 as *"a 12x improvement that can reduce expenses for long-running agent workflows"* [8,11]. At original Aug 2024 launch there was only one (5-minute-equivalent) tier — no TTL choice existed yet [10].
- **Pricing multipliers (exact, current)**: 5-min cache **write** = **1.25×** base input price; 1-hour cache **write** = **2×** base; cache **read** = **0.1×** base, except **0.05×** for Claude Opus 5.5 and **0.025×** for Claude Fable/Mythos 5.1 [8,9]. At Aug 2024 launch: write = base × 1.25 (25% more), read = base × 0.1 (10% of base) — i.e., the read-side multiplier has been stable since 2024; the write-side 1.25×/2× split by TTL and the per-model read exceptions are later refinements [8–10].
- **Minimum cacheable tokens**: varies by model — **512** tokens (Opus 5.5, Opus 5, Sonnet 5.5, Fable/Mythos 5/5.1), up to **4,096** (Opus 4.6/4.5, Haiku 4.5), **1,024** for several Opus/Sonnet 4.x models [8].
- **Supported models**: *"Prompt caching (both automatic and explicit) is supported on all active Claude models"* [8].
- **Invocation**: explicit breakpoints via `cache_control` on content blocks (max 4 per request, 20-block lookback window); **"automatic caching"** (single top-level `cache_control` field, auto-advances the breakpoint) launched **Feb 19, 2026** [8,12].
- **2026 additions**: **cache diagnostics** (compares current vs. a prior request, reports first point of divergence — model/system/tools/history — that broke a cache hit) went to public beta ~Apr 2026 and **GA Sept 23, 2026** [12]. Claude Opus 5.5 (Sept 22, 2026) carries the special 0.05× cache-read multiplier [12].
- **Related feature**: "context editing" + memory tool (public beta, ~Sept 2025) — *"combining the memory tool with context editing improved performance by 39% over baseline. Context editing alone delivered a 29% improvement"*; a 100-turn web-search eval showed *"reducing token consumption by 84%"* [8] (date of this post itself is **UNVERIFIED** to the day; inferred from its tie to Claude Sonnet 4.5's launch).
- **UNVERIFIED (flagged as disputed)**: a third-party claim that the default TTL was briefly changed is **contradicted** by every primary Anthropic source opened this session, which show 5-minute-default/1-hour-optional unchanged in structure since May 2025 [8,10,11].

### Google — Gemini caching & Gemma architecture

**Gemini context caching** — `ai.google.dev/gemini-api/docs/generate-content/caching` [13]; Vertex/Enterprise Agent Platform docs [14]; pricing [15].

- **Implicit (automatic)**: *"enabled by default on Gemini 2.5 and newer models... no cost saving guarantee"* [13].
- **Explicit (manual)**: created via `client.caches.create()`; *"cost saving guarantee"* [13].
- **Discount**: implicit — *"a 90% discount on cached tokens compared to standard input tokens"*, flat across supported models; explicit — *"On Gemini 2.5 or later models, this discount is 90%; on Gemini 2.0 models, this discount is 75%"* [14].
- **Minimum tokens** (public API): Gemini 3.8/3.7/3.6/3.5 Flash and 3.1 Pro Preview = **4,096**; Gemini 2.5 Flash/Pro = **2,048** [13]. Vertex raises the implicit floor to **6,144** for several of the same models [14] — a confirmed API-vs-Vertex discrepancy.
- **TTL**: default **1 hour** if unset; minimum **1 minute**; *"there isn't a maximum cache duration"* [13,14]. Only explicit caching incurs storage cost; implicit has none [14].
- **Pricing (Gemini 3.8 Flash, Standard tier)**: input $0.75/M → cache read $0.075/M (exactly 10% = 90% off); storage $0.50/M tokens/hour [15].

**Gemma 2** — arXiv 2408.00118 [16]: *"We alternate between a local sliding window attention... and global attention... in every other layer. The sliding window size of local attention layers is set to 4096 tokens, while the span of the global attention layers is set to 8192 tokens."* **Ratio 1:1**, confirmed across 2B/9B/27B sizes.

**Gemma 3** — arXiv 2503.19786 [16]: *"5:1 interleaving of local/global layers... a pattern of 5 local layers for every global layer"*, local window = **1024 tokens** (global RoPE base raised 10k→1M). **KV-memory figure (exact, but for a separate ablation, not the literally-shipped 5:1 config)**: *"the 'global only' configuration results in a memory overhead of 60%, while this is reduced to less than 15% with 1:3 and sliding windows of 1024"* — this specific 60%→<15% pair is measured at a **1:3** ratio on a 2B model, isolating the `sw=1024` effect; the paper separately plots (Fig. 6) KV memory vs. context length for the actual shipped 5:1 architecture without attaching a second standalone percentage in prose.

**Gemma 3n** — official dev blog [16]: *"KV Cache Sharing... The keys and values of the middle layer from local and global attention are directly shared with all the top layers, delivering a notable 2x improvement on prefill performance compared to Gemma 3 4B."* Plus Per-Layer Embeddings (PLE): E2B has >5B total params but *"effective memory load of just under 2 billion (1.91B) parameters."* Context: 32K tokens.

**Gemma 4 (2026)** — arXiv 2607.02770 [16]: *"We conserve a 5:1 ratio of local sliding window to global self-attention (4:1 for the 2.3B model)... Combined with KV cache sharing and the reuse of keys as values in global layers, these optimizations reduce the global KV cache footprint by up to 37.5%."* Also: *"share the KV cache with ratios of 20/35 and 18/42 for the E2B and E4B model."* Table: 31B model at 32K context = 64.0GB weights (bf16) + only **1.10GB KV** (≈1.7% overhead). Exact sliding-window token size for Gemma 4 is **UNVERIFIED** (not located in the portion of the paper read). Announcement date is **UNVERIFIED to the exact day** (URL path implies March 2026; a secondary source claims April 2, 2026, not independently confirmed) [16].

### Meta — Llama 4 iRoPE / chunked attention

Official blog [25]; HF config (community mirror, cross-verified against `huggingface/transformers` source) [26].

- **iRoPE, exact definition**: *"A key innovation in the Llama 4 architecture is the use of interleaved attention layers without positional embeddings. Additionally, we employ inference time temperature scaling of attention to enhance length generalization. We call this the iRoPE architecture, where 'i' stands for 'interleaved' attention layers, highlighting the long-term goal of supporting 'infinite' context length, and 'RoPE' refers to the rotary position embeddings employed in most layers."* [25] **The blog's own prose never states a numeric chunk size and never uses the word "chunk."**
- **Context claims (blog)**: *"Llama 4 Scout dramatically increases the supported context length from 128K in Llama 3 to an industry leading 10 million tokens."* Pre/post-trained at 256K context length [25].
- **Config.json (exact fields, `text_config`)**: `attention_chunk_size: 8192`; `attn_temperature_tuning: true`; `floor_scale: 8192`; `attn_scale: 0.1`; `use_qk_norm: true`; `no_rope_layers`: 48-entry array = `[1,1,1,0]` × 12 (every 4th layer, i.e. 12 of 48, is NoPE/global; the rest use RoPE); `max_position_embeddings: 10485760` (exactly 10×2²⁰ = "10M"); `cache_implementation: "hybrid"`; `num_attention_heads: 40`, `num_key_value_heads: 8` (GQA) [26]. Independently corroborated by `huggingface/transformers:src/transformers/models/llama4/configuration_llama4.py`, which documents identical defaults: *"attention_chunk_size... defaults to 8192: Chunk size for the attention computation. Smaller value enforces more local attention and lowers memory."* [26]
- Secondary technical source (vLLM blog, not Meta's own words): *"Llama 4 interleaves global attention (without RoPE) with chunked local attention (with RoPE) in a 1:3 ratio. The local attention layer attends to tokens in non-overlapping chunks..."* [26]
- **Notable 2026 finding**: no verified "Llama 4.5" or "Llama 5" exists on primary Meta channels as of 2026-10-04 (`huggingface.co/meta-llama` and `github.com/meta-llama/llama-models` still list Llama 4 as current). Meta's newest 2026 model releases are branded **"Muse"** (Spark/Glimmer/Image/Voice Transcribe) and "SAM 3.1" under new `meta-models` orgs; their attention/KV-cache architecture was **not fetched** (out of scope) [25].

### DeepSeek

**MLA** — arXiv 2405.04434 [17]: headline — *"Compared with DeepSeek 67B, DeepSeek-V2... reduces the KV cache by 93.3%"*. Table 1 (formulas, KV cache elements per token): MHA = `2·n_h·d_h·l`; GQA = `2·n_g·d_h·l`; MQA = `2·d_h·l`; **MLA ≈ `(9/2)·d_h·l`**, footnote: *"its KV cache is equal to GQA with only 2.25 groups, but its performance is stronger than MHA."* Table 9 (controlled ablation, matched architecture): small MoE — MHA 110.6K vs. MLA **15.6K** elements/token (**14%**); large MoE — MHA 860.2K vs. MLA **34.6K** (**4%**); paper's own words: *"MLA requires a significantly smaller amount of KV cache (14% for small MoE models and 4% for large MoE models) than MHA."*

**Context caching on disk** — announced 2024-08-02 [18]: *"caches content that is expected to be reused on a distributed disk array... This is made possible by the MLA architecture in DeepSeek V2."* Mechanics: prefix match **from token 0 only**; **64-token** storage granularity; unused entries auto-clear in hours-to-days. Latency: *"a 128K prompt... first token latency is cut from 13s to just 500ms."* Original pricing: cache hit $0.014/M vs. miss $0.14/M (10×). **Current (2026) pricing** (peak = 01:00–04:00 & 06:00–10:00 UTC Mon–Fri; off-peak = half of peak): `deepseek-flash` cache hit off-peak **$0.003/M** vs. miss off-peak **$0.15/M** (50×); `deepseek-v4-pro` hit off-peak **$0.022/M** vs. miss **$0.66/M** (30×) [18].

**DeepSeek Sparse Attention (DSA)** — `deepseek-ai/DeepSeek-V3.2-Exp` repo + in-repo paper [17]: *"DSA, a fine-grained sparse attention mechanism powered by a lightning indexer."* Indexer: `I_{t,s} = Σ w^I_{t,j}·ReLU(q^I_{t,j}·k^I_s)` (ReLU "for throughput," FP8-capable); top-k selection retrieves only entries where `I_{t,s} ∈ Top-k(I_{t,:})`. Exact config: `index_n_heads: 64`, `index_head_dim: 128`, `index_topk: 2048`. *"DSA reduces the core attention complexity of the main model from O(L²) to O(Lk)."* Implemented "based on the MQA mode of MLA." Benchmark parity example: MMLU-Pro 85.0 vs. 85.0 (V3.1-Terminus vs. V3.2-Exp) [17].

**2026 roadmap (official changelog, `api-docs.deepseek.com/news/`)** [18]: **DeepSeek-V3.2** official successor, Dec 1, 2025. **DeepSeek-V4 Preview**, Apr 24, 2026 — *"Novel Attention: Token-wise compression + DSA... Peak Efficiency: World-leading long context with drastically reduced compute & memory costs. 1M Standard: 1M context is now the default."* V4-Pro: 1.6T total/49B active params; V4-Flash: 284B total/13B active. V4-Pro GA Aug 13, 2026; V4.1-Flash Sept 10, 2026. No V5 found as of 2026-10-04.

### Moonshot AI / Kimi

**Mooncake** (KV-centric disaggregated serving) — `kvcache-ai/Mooncake` [19]; FAST'25 paper (Best Paper Award) [20]; arXiv [21].

- **Architecture, 2024 paper terms**: global scheduler **"Conductor"** (*"dispatching requests based on the current distribution of the KVCache and workloads"*) + RDMA transfer component **"Messenger"** + a **"Distributed KVCache Pool"** across CPU/DRAM/SSD [21].
- **Architecture, live 2026 README** (terminology has moved on — "Messenger" returns **zero** hits in a code search of the current repo): *"a KV cache-centric disaggregated architecture that separates prefill and decode clusters, while leveraging otherwise underutilized CPU, DRAM, and SSD resources... Transfer Engine for low-latency data movement... Mooncake Store for distributed KV cache and model-weight management... Mooncake EP & PG for elastic MoE serving."* "Conductor" persists but is now scoped as *"the kv-cache indexer used by cache-aware routers"* [19].
- **Numbers (version-dependent — cite carefully)**: FAST'25 camera-ready abstract: *"increases the effective request capacity by 59%∼498%... processing over 100 billion tokens daily... enables Kimi to handle 115% and 107% more requests on NVIDIA A800 and H800 clusters"* [20]. arXiv v4 (updated 2025) / current live README: *"up to a 525% increase in throughput in certain simulated scenarios... enables Kimi to handle 75% more requests"* [19,21].
- **Transfer Engine bandwidth**: *"up to 87 GB/s and 190 GB/s... in 4×200 Gbps and 8×400 Gbps RoCE networks... about 2.4x and 4.6x faster than TCP"*, moving 40GB (= KV cache of 128K tokens, LLaMA3-70B) [19].
- **KV reuse rate**: *"Theoretically, up to only 50% of the KVCache can be reused... can be as large as 90% for certain scenarios, such as our chat-to-paper service"* [21].
- **Production**: *"Mooncake is the serving platform for Kimi"*; Jul 20, 2025 changelog entry — Kimi K2 on 128 H200 GPUs, PD disaggregation, **224k tok/s prefill, 288k tok/s decode** [19].

**Kimi Linear** — arXiv 2510.26692, GitHub `MoonshotAI/Kimi-Linear`, HF model card [22]: *"Kimi Linear interleaves KDA with periodic full attention layers in a uniform 3:1 ratio... reduces memory and KV-cache usage by up to 75% during long-sequence generation."* Core mechanism: **Kimi Delta Attention (KDA)**, extending Gated DeltaNet with finer-grained gating; fixed-size state (`dk=dv=128` per head) regardless of sequence length. Ablation (Table 1) confirms 3:1 empirically beat 7:1 and 1:1 alternatives. Decoding speedup: **6.3×** faster TPOT at 1M tokens (1.84ms vs. 11.48ms, includes batch-size reallocation benefit) or a more conservative **2.3×–3.98×** (raw attention-kernel-only, excluding batch effects). Model: 3B activated/48B total params, 1M context, 5.7T training tokens. Benchmarks: RULER 128K = 84.3 (vs. MLA's 81.3) with 3.98× speedup.

### Microsoft

**YOCO ("You Only Cache Once")** — arXiv 2405.05254 [28]: *"a decoder-decoder architecture, YOCO, for large language models, which only caches KV pairs once. Specifically, we stack cross-decoder upon self-decoder. Given an input sequence, the self-decoder utilizes efficient self-attention [gated retention] to obtain KV caches. Then the cross-decoder layers employ cross-attention to reuse the shared KV caches."* Numbers: *"the memory of KV caches can be reduced by about 80× for 65B models... for a 3B model... reduced by two times for 32K tokens and by more than nine times for 1M tokens."* Prefill: *"speeded up by 71.8× for the 1M context and 2.87× for the 32K input... reduces the Transformer prefilling latency from 180 seconds to less than six seconds"* (512K context). GitHub: `microsoft/unilm/tree/master/YOCO`.

**Phi-4-mini-flash-reasoning / SambaY** — arXiv 2507.06607, HF model card, Azure blog (~July 9, 2025) [29]: *"We introduce the Gated Memory Unit (GMU)... We apply it to create SambaY, a decoder-hybrid-decoder architecture that incorporates GMUs in the cross-decoder to share memory readout states from a Samba-based self-decoder... replaces half of the cross-attention layers with GMUs... Since around 50% of expensive cross-attention layers are replaced with cheap element-wise gating, SambaY significantly improves decoding efficiency."* Self-decoder = Mamba (SSM) + Sliding Window Attention + one full-attention layer. Official claim: *"up to 10 times higher throughput and a 2 to 3 times average reduction in latency"* (2K prompt / 32K generation, vLLM, single A100-80GB). 3.8B params, 64K context.

**Other MSR KV papers found** [30]: **Samba** (arXiv 2406.07522, ICLR 2025, direct architectural ancestor of SambaY): *"3.73x higher throughput compared to Transformers with GQA for... 128K length, and 3.64x speedup... generating 64K tokens."* **SCBench** (arXiv 2412.10319, ICLR 2025): a *"KV cache-centric"* benchmark across 4 stages (generation/compression/retrieval/loading); finding: *"sub-O(n) memory methods suffer in multi-turn scenarios... layer-level sparsity in hybrid architectures reduces memory usage with strong performance."* **R-KV** (arXiv 2505.24133): *"preserves nearly 100% of the full KV cache performance using only 10% of the KV cache... a 90% memory saving and a 6.6X throughput."* No "Phi-5"/"Phi-4.5" found as of 2026-10-04.

### NVIDIA

**TensorRT-LLM** [31]: **KV cache reuse** (paged blocks shared across requests with a common prefix) — *"can significantly accelerate inference for use cases requiring system prompts by up to 5x"*; **host-memory offload** — *"accelerate time to first token (TTFT) by up to 14x on... H100... and 28x on the... GH200 Superchip"*; block-size tuning — *"speed up TTFT up to 7%"* (Llama-70B/H100, 64→8 tokens/block). **FP8 KV cache** supported (`KvCacheConfig(dtype='fp8')`). **NVFP4 KV cache** (new): *"cuts KV cache memory footprint by up to 50%... <1% accuracy loss... up to 3x better time-to-first-token (TTFT)... 5% higher accuracy... versus MXFP4"* (Llama 3.3 70B). A newer **"Cold-Page Quantization (NVFP4)"** framework stores cold/offloaded KV blocks in NVFP4 while GPU-resident cache keeps native dtype (FP16/BF16/FP8); ships alongside **TriAttention** (ICML 2026, arXiv 2604.04921) for generation-time token eviction/compaction.

**NVIDIA Dynamo — KV Block Manager (KVBM)** [33]: *"a scalable runtime component... for memory allocation, management, and remote sharing of Key-Value (KV) blocks... across heterogeneous and distributed environments... a unified memory layer and write-through cache for frameworks like vLLM and TensorRT-LLM."* Tiers: **G1** (GPU HBM) → **G2** (pinned DRAM) → **G3** (NVMe/SSD) → **G4** (S3/MinIO). Support matrix: vLLM ✅, TensorRT-LLM ✅, **SGLang ❌**. Launch (GTC 2025): *"boosts the number of requests served by up to 30x, when running... DeepSeek-R1... on... Blackwell."* KVBM-specific offload benchmarks: Vast Data *"35 GB/s throughput to a single... H100 GPU"*; WEKA *"read throughput up to 270 GB/s across eight GPUs."* **Dynamo 1.0 GA** (GTC 2026, March): *"boosts inference performance of... Blackwell GPUs by up to 7x."* 2026 agentic-inference blog: *"97.2% aggregate cache hit rate across 4 Opus teammates. An 11.7x read/write ratio."*

**kvpress** [34]: README's own framing: *"kvpress implements multiple KV cache compression methods and benchmarks using 🤗 transformers, aiming to simplify the development of new methods for researchers and developers in this field."* Methods implemented (exact, non-exhaustive list from README): `RandomPress`, `KnormPress`, `SnapKVPress`, `ExpectedAttentionPress`, `StreamingLLMPress`, `TOVAPress`, `ObservedAttentionPress`, `PyramidKVPress`, `AdaKVPress`, `SimLayerKVPress`, `DuoAttentionPress`, and ~15 others. **H2O (Heavy-Hitter Oracle) is confirmed absent** from the list. Full-text grep of the 353-line README for "vllm"/"tensorrt" returned **zero matches** — no stated production-serving integration path.

### Character.AI

Official post, "Optimizing AI Inference at Character.AI" [38], published **2024-06-21** (confirmed via `article:published_time` + Wayback Machine capture 2024-06-20); still the latest — no 2025/2026 technical follow-up found [39,40].

- **MQA**: *"We adopt Multi-Query Attention (Shazeer, 2019) in all attention layers. This reduces KV cache size by 8X compared to the Grouped-Query Attention adopted in most open source models."* — ⚠️ **the 8× figure is stated vs. GQA, not vs. plain MHA.**
- **Hybrid local/global attention**: *"We interleave local attention with global attention layers... reducing attention horizon to 1024 on most attention layers... In our production model, only 1 out of every 6 layers uses global attention."*
- **Cross-layer KV sharing**: *"We tie the KV cache across neighboring attention layers, which further reduces KV cache size by a factor of 2-3x. For global attention layers, we tie the KV cache of multiple global layers across blocks..."* (cites Brandon et al. 2024, CLA, arXiv 2405.12981).
- **int8**: *"We use int8 quantization on model weights, activations, and attention KV cache... we natively train our models in int8 precision."* No standalone numeric factor given for this component alone.
- **Cache rate**: *"Our system achieves a 95% cache rate"* (sticky-session routing; exact term is "cache rate," not "hit rate").
- **Combined**: *"We use the following techniques to reduce KV cache size by more than 20X without regressing quality."* (This figure covers MQA + hybrid attention + cross-layer sharing; the 95% cache rate and int8 quantization are reported as separate, additional optimizations, not multiplied into the "20X.")

### Inference engines

**vLLM** [41,42,44,45,46,47]:
- **PagedAttention** (original 2023 blog): *"partitions the KV cache of each sequence into blocks... blocks as pages, tokens as bytes, sequences as processes."* Existing (pre-vLLM) systems *"waste 60% – 80% of memory due to fragmentation and over-reservation"*; PagedAttention cuts this to *"under 4%"*. Parallel-sampling memory sharing: *"cutting their memory usage by up to 55%"* → *"up to 2.2x improvement in throughput."* Overall: *"up to 24x higher throughput compared to HF"* / *"3.5x higher... than TGI."*
- **Automatic Prefix Caching**: hash-based block reuse; block hash = `hash(parent_hash, block_tokens, extra_hashes[LoRA/mm/salt])`. Default hash algo `sha256` since v0.11 (alternatives: `xxhash`, `*_cbor`). Only full blocks cached; LRU eviction. Explicit limitation: *"APC only reduces the time of processing the queries (the prefilling phase) and does not reduce the time of generating new tokens (the decoding phase)."*
- **FP8 KV cache**: per-tensor or per-attention-head quantization; `kv_cache_dtype` = `fp8_e4m3`/`fp8_e5m2`. Blog (Apr 22, 2026): 128K-context NIAH accuracy on Hopper fell *"from 91% (BF16 baseline) to just 13%"* before a fix, restored to *"89%"*; throughput-under-load: *"14.9% higher output throughput"* (Llama-3.1-8B FP8) / *"4.8% higher"* (gpt-oss-20b, FP8 skip sliding-window layers).
- **KV offloading / disaggregation**: `KVConnectorBase_V1` API with 9 documented connector types (LMCacheConnectorV1 via NIXL, NixlConnector, MooncakeConnector, OffloadingConnector (CPU), etc.). Tiered offloading blog (available since v0.22): beyond 128 concurrent conversations when HBM+CPU both fill, storage offloading is *"more than doubling throughput"* vs. no offloading. Disaggregated-serving guide: collocated *"p99 is about six times higher"* than disaggregated P/D at matched median latency (2×L40S, Qwen2.5-7B); stated KV size *"Llama-3.1-70B in BF16 stores 320 KiB per token."*

**SGLang** [43,48]:
- **RadixAttention** (2024 paper/blog): *"retains the KV cache for both prompts and generation results in a radix tree... enables efficient prefix search, insertion, and eviction... LRU eviction policy... up to 5 times higher throughput compared to existing systems, namely Guidance and vLLM."*
- **HiCache** (Sept 10, 2025 blog + docs): *"Inspired by the classic three-level cache design of modern CPUs, HiCache organizes GPU memory as L1, host memory as L2, and distributed storage as L3."* L3 backends: Mooncake, DeepSeek 3FS, NIXL. GPU-assisted I/O: *"up to 3× higher transfer speed"*; layout decoupling + zero-copy: *"up to 2× higher throughput."* Production partner numbers: **Novita AI** (Qwen3-Coder-480B) — *"average TTFT dropped by 56%, inference throughput doubled, and the cache hit rate jumped from 40% to 80%"*; **Ant Group** (DeepSeek-R1-671B) — *"an 84% reduction in TTFT"*; SGLang's own benchmark — *"up to 6× throughput improvement and up to 80% reduction in TTFT."*

**llama.cpp** [35]: flags `-ctk/--cache-type-k` and `-ctv/--cache-type-v`, allowed values `f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1` (default `f16`). Source-level hard constraint (`src/llama-context.cpp`): quantized **V-cache** auto-enables flash-attention when `-fa auto` (default), or hard-errors at load time (*"quantized V cache requires flash_attn to be enabled"*) when `-fa off` is explicit. Quantized KV cache is **not implemented** at all under `--split-mode tensor` (explicit runtime error).

**LMCache + CacheGen** [36]: LMCache = *"a KV cache management layer for LLM inference... turns KV cache from a temporary state into reusable AI-native knowledge... reduces TTFT... and improves throughput."* Pluggable backends: CPU RAM, disk, Redis/Valkey, Mooncake, InfiniStore, S3, NIXL, GDS; supports non-prefix reuse via CacheBlend. CacheGen (arXiv 2310.07240, SIGCOMM 2024): *"reduces the KV cache size by 3.5-4.3x and the total delay in fetching and processing contexts by 3.2-3.7x with negligible impact on... quality."*

**Ollama** [37]: `OLLAMA_KV_CACHE_TYPE` env var (requires Flash Attention enabled), default `f16`; `q8_0` — *"uses approximately 1/2 the memory of f16 with a very small loss in precision... usually has no noticeable impact"*; `q4_0` — *"approximately 1/4 the memory... small-medium loss... may be more noticeable at higher context sizes."* Note: *"Models that have a high GQA count (e.g. Qwen2) may see a larger impact on precision from quantization."*

**Together.ai / Fireworks.ai / Baseten / Groq** [49–53]:
- **Together.ai**: official blog, "Cache-aware prefill–decode disaggregation (CPD)" (Mar 4, 2026): *"up to 40% higher sustainable throughput"* for long-context serving by separating cache-hit ("warm") from new-context ("cold") requests onto separate compute. A related arXiv paper (OSCAR, 2605.17757, *"reduces KV-cache memory by approximately 8x"*) is attributed to Together AI by third parties, but **no official together.ai blog post confirming this was found — UNVERIFIED.**
- **Fireworks.ai**: FireAttention blog — explicit KV-shrinking motivation (*"as memory bandwidth is the bottleneck during generation, we should try to shrink both weights and key/value caches"*), *"4x speedup"* vs. OSS baselines, FP8 *"shrinks model size 2x"*, *"2x improvement of... requests/second"* (Mixtral-8x7B, 8×H100). FireAttention V2: *"~1.7x in fp16 and ~5.6x in fp8"* throughput vs. vLLM (broader attention/long-context speedup, not KV-cache-specific).
- **Baseten**: public "Inference Engineering" book, §5.3 Caching, gives an explicit KV storage-tier table (G1 device memory→G4 networked SSD) and a worked example (*"16 GB of KV cache alone"* for Llama-3.1-8B/128K/one session). A separate blog analyzing Google Research's TurboQuant/PolarQuant (*"compresses the KV cache by over 4.2x"*) is explicit that Baseten had **not yet shipped** this: *"Coming soon? We'll try to cook something here at Baseten."*
- **Groq**: no official content on internal LPU KV-cache architecture found. Only a generic prefix-level *"Prompt Caching"* doc exists (*"reducing latency and token costs by 50% for cached portions... expires after 2 hours"*) — it never uses the term "KV cache."

## Does ANY provider ship lossy token eviction (H2O/SnapKV-style) in production?

**Evidence found: no.** Across every primary source opened in this session — OpenAI, Anthropic, Google, Meta, DeepSeek, Moonshot, MiniMax, Qwen, Microsoft, Apple, NVIDIA, Character.AI, vLLM, SGLang, llama.cpp, LMCache, Ollama, Together.ai, Fireworks.ai, Baseten, Groq — **none** describe a production/default serving path that performs heuristic, irreversible eviction of KV-cache entries mid-generation in the H2O/SnapKV/StreamingLLM sense (scoring tokens by attention mass or recency and discarding the losers to fit a fixed budget).

What the evidence instead shows, directly:

1. **The single most direct, named piece of evidence is NVIDIA's own kvpress** [34]. It is the one project found in this entire survey that explicitly implements SnapKV, StreamingLLM, TOVA, PyramidKV, AdaKV, and ~20 other eviction/merging methods — i.e., NVIDIA itself built and maintains the reference implementation of this technique family. Yet its own README states its purpose is to **"simplify the development of new methods for researchers and developers"** on top of 🤗 Transformers, and a full-text search of the README found **zero mentions of vLLM or TensorRT-LLM** (NVIDIA's own production serving stacks). It is also missing H2O itself. This is as close to a direct admission as exists in the primary-source record: NVIDIA's production stack (TensorRT-LLM, Dynamo) ships paging, reuse, offloading, and FP8/NVFP4 quantization [31,33] — not kvpress's eviction methods.
2. **DeepSeek's "sparse attention" is easy to mistake for eviction but is explicitly not** — the lightning indexer in DSA selects a top-k subset of tokens *to attend to per query*, while the full KV cache for every prior token remains resident in memory; nothing is discarded [17]. This distinction matters precisely because DSA is the one "selective attention" mechanism found that *is* in real production (DeepSeek's API), and it works by leaving the cache lossless while making compute sparse — the opposite of what H2O/SnapKV do (which keep compute dense but make the *cache* lossy).
3. Every production provider instead converges on three alternative levers, all independently confirmed multiple times above: **(a) lossless reuse** — prefix/context caching (OpenAI/Anthropic/Google/DeepSeek), radix/hash-based engine-level caching (vLLM/SGLang/TensorRT-LLM), and multi-tier offloading/disaggregation (Dynamo/Mooncake/LMCache/HiCache); **(b) architectural change decided once at training time** — MQA/GQA (near-universal), MLA (DeepSeek), sliding-window/hybrid-global interleaving (Gemma/gpt-oss/Llama4/Character.AI/Apple), cross-layer/cross-block KV sharing (Character.AI/Apple/Gemma 3n&4/YOCO-lineage), and hybrid linear attention (Qwen3-Next family/Kimi Linear, though contested by MiniMax's reversal); **(c) numeric quantization of the retained cache** — FP8/NVFP4 (NVIDIA), INT8 (Character.AI, native-trained), and 4–8-bit (llama.cpp/Ollama/MLX-LM).
4. The nearest things to "lossy inference-time compression actually shipped to end users" found are **quantization** (which is lossy in precision but keeps every token's cache entry, unlike eviction which discards entire tokens) and **TensorRT-LLM's newly-documented TriAttention** (ICML 2026) for "generation-time token eviction/compaction" [31] — this is the single closest primary-source hit to production eviction, but it is documented as part of a "KV Cache Compression" framework alongside cold-page quantization, not described with adoption/usage numbers, and was not found referenced anywhere else (NVIDIA blogs, Dynamo, vLLM, SGLang) as of this session — treat as an emerging, not yet broadly confirmed, production feature.

If anything changes this picture, it would have to be a primary source explicitly stating an eviction method (H2O, SnapKV, StreamingLLM-style sink+window, TOVA) is the **default or recommended** configuration in a named production serving stack — no such statement was found in this session.

## Where a student team could borrow from — or beat — production practice (1–3B, laptop scale)

The production techniques that are **free to borrow outright** at 1–3B scale are the ones that cost nothing and are already present in most open-weight small models: **GQA** (gpt-oss, Llama 4, Gemma, Qwen, and essentially every current 1–3B release already ship it — check the base model's `config.json` for `num_key_value_heads < num_attention_heads` before doing any extra work), and **prefix/radix caching** for repeated system prompts or multi-turn evaluation harnesses (SGLang's RadixAttention and vLLM's Automatic Prefix Caching are both small, well-documented, hash-the-block-and-reuse algorithms [42,43] that are pure engineering with zero quality risk and are directly reimplementable for a single-process benchmark harness). **KV-cache quantization** is also a safe, well-trodden lever — llama.cpp/Ollama/MLX-LM all confirm 8-bit KV cache is close to free quality-wise (`q8_0`: *"very small loss in precision... usually no noticeable impact"* [37]) and is a one-line flag — but the vLLM FP8 story (91%→13%→89% NIAH accuracy around a subtle numerical bug [45]) is a direct, citable warning that quantization must be validated on a long-context recall benchmark, not just perplexity, before trusting it. Conversely, the giant **fleet-level, multi-GPU distributed serving infrastructure** (NVIDIA Dynamo's KVBM, Mooncake's disaggregated prefill/decode, vLLM's cross-node tiered offloading) is solving a different problem — maximizing cache-hit rate and throughput across thousands of concurrent users on a GPU cluster — and is irrelevant at laptop/single-GPU, single-session scale; a hackathon team should not try to reproduce it.

Where a student team is in a genuinely under-served position relative to big labs, and could plausibly **beat** documented production practice on the specific axis the problem asks about (compressing a *fixed, already-trained* small model's KV cache at *inference time*, not retraining it), is exactly the gap this research surfaced: **no major lab has hardened lossy token eviction (H2O/SnapKV/StreamingLLM-style) into a production serving default** — it lives only in NVIDIA's own research/benchmarking library, kvpress, which by its own README exists to help outside researchers develop and evaluate these methods [34], not because the technique doesn't work, but because frontier labs with the budget to retrain can get equivalent savings "for free" by changing the architecture once (MLA, GQA, hybrid linear attention, cross-layer sharing) rather than taking an inference-time accuracy risk on every request at enormous scale. A hackathon team working with a *fixed* 1–3B open-weight checkpoint cannot retrain a new architecture from scratch, so inference-time compression is the only lever actually available to them — which means a careful, honestly-evaluated eviction/merging implementation (e.g., SnapKV's query-aware scoring, or a StreamingLLM-style sink+window baseline, both already provided as starter baselines) compared head-to-head against (1) the architectural "free lunches" already in the base model, (2) 8-bit KV quantization stacked on top, and (3) a from-scratch cross-layer KV-sharing retrofit inspired by Character.AI/Apple/YOCO's 2–3×/37.5%/80× results [38,27,28] — reported on recall-of-earlier-content and downstream accuracy at a fixed memory budget — is a genuinely open, citable comparison that no single production source in this survey currently publishes for models at this size. The multiplicative stacking is the key insight every production source demonstrates (DeepSeek stacks MLA + disk caching [17,18]; Character.AI stacks MQA + hybrid attention + cross-layer tying + int8 + prefix caching [38]; Gemma 4 stacks sliding-window ratio + key-as-value reuse + cross-layer sharing [16]) — a student team should likewise combine quantization (nearly free) with one well-evaluated eviction or merging method (the actually novel contribution), rather than treating them as alternatives.
