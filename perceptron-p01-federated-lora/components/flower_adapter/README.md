# C10 Flower adapter

This folder wraps the existing in-process LoRA simulator in Flower 1.39's Message API. It does **not** reimplement aggregation: `FlowerLoraStrategy` delegates to `components.aggregator.strategies.make_strategy`, sends the same `client_view`, receives each strategy's `payload`, and calls the same `aggregate` used by `components.orchestrator.simulate.run_experiment`.

## Flower 1.39 APIs used

Read from the installed source:

- `.venv/lib/python3.11/site-packages/flwr/clientapp/client_app.py`: `ClientApp`, `@app.train()`, and `Message` reply handling.
- `.venv/lib/python3.11/site-packages/flwr/serverapp/server_app.py`: `ServerApp` and `@app.main()`.
- `.venv/lib/python3.11/site-packages/flwr/serverapp/strategy/strategy.py`: message-based `Strategy.start`, `configure_train`, `aggregate_train`, and server-side `evaluate_fn`.
- `.venv/lib/python3.11/site-packages/flwr/serverapp/grid/grid.py`: `Grid.create_message`, `send_and_receive`, and `get_node_ids`.
- `.venv/lib/python3.11/site-packages/flwr/app/message/{arrayrecord,configrecord,metricrecord,recorddict,message,context}.py`: `ArrayRecord`, `ConfigRecord`, `MetricRecord`, `RecordDict`, `Message`, and `Context`.
- `.venv/lib/python3.11/site-packages/flwr/simulation/app.py`: the packaged simulation runtime still defaults to a Ray backend, so the demo uses a tiny in-process `LocalGrid` instead of installing Ray.

## Contract mapping

- `ClientTask` fields are carried in the outbound `ConfigRecord` (`round`, `client_id`, `rank`, `planned_steps`, `allowed_steps`, `batch_size`, `lr`, `train_A`, `seed`).
- LoRA layer states are carried as `ArrayRecord` tensors with a companion schema `ConfigRecord` listing layer names.
- Client replies carry strategy payload tensors plus a `meta` `ConfigRecord` matching `ClientUpdate` (`n_examples`, `planned_steps`, `steps_done`, status, upload bytes, wall time).
- Server aggregation emits the same `AggregationReport` fields internally and evaluates with `components.local_trainer.evaluate` every `eval_every` rounds/final round.

Availability is still generated by `availability_schedule`. Offline devices are not messaged. Deadline-cut devices are messaged only when the selected strategy has `accept_partial=True`; otherwise they become `late_discarded`, matching the reference loop.

## Run

```bash
cd perceptron-p01-federated-lora
source .venv/bin/activate
pytest -q tests/test_flower_adapter.py
python -m components.flower_adapter.run_demo
```

The demo uses `ExperimentConfig(strategy="anchor_full", scenario="dropout", rounds=2, exclude=("c1", "c4"), batch_size=1)` and `load_world`, which loads SmolLM2-135M with `local_files_only=True` through the existing trainer code.

## Parity result

The fast CPU test passes without loading the LLM. Attempted `python -m components.flower_adapter.run_demo` in the shared environment. It loaded the local SmolLM2 world and entered `FlowerLoraStrategy.start`, but produced no first-round result after ~15 minutes on the heavily shared MPS/CPU host, so I stopped it. No parity numbers were observed in this session; `run_demo.py` prints the two final macro losses and absolute difference when run on an unloaded prepared machine.

## Killing a node mid-run

For this no-Ray local demo, a node can be removed from future rounds with `LocalGrid.kill_node(node_id)`; pending messages to that node receive no reply, which exercises the same partial-reply server path. In a full Flower deployment, the equivalent is stopping the SuperNode process. The packaged `flwr-simulation` path defaults to Ray in 1.39, so this adapter intentionally avoids Ray for the hackathon demo.
