## Notes

### 1. Kubernetes HorizontalPodAutoscaler (HPA) — docs, production
URL: https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/ (accessed 2026-10-04)
- "Kubernetes implements horizontal pod autoscaling as a control loop that runs intermittently (it is not a continuous process). The interval is set by the `--horizontal-pod-autoscaler-sync-period` parameter to the `kube-controller-manager` (and the default interval is **15 seconds**)."
- Purely reactive: queries current resource utilization each period against the target metric, no demand forecasting is part of core HPA.
- "The controller considers all recommendations within a configurable window choosing the highest recommendation from within that window. You can configure this value using the `--horizontal-pod-autoscaler-downscale-stabilization` command line option, which **defaults to 5 minutes**. This means that scaledowns will occur gradually, smoothing out the impact of rapidly fluctuating metric values." — i.e. the only "shock" protection is a one-sided (downscale-only) stabilization window; scale-up reacts immediately (modulo the 15s loop), which is the classic reactive-autoscaler weakness during abrupt demand spikes (cold-start lag while new pods boot).
- Pod readiness tuning: `--horizontal-pod-autoscaler-cpu-initialization-period` (default 5 min) ignores CPU readings from just-started pods; `--horizontal-pod-autoscaler-initial-readiness-delay` (default 30s) treats flapping-ready pods as still-initializing — both exist to stop noisy pod-boot metrics from corrupting the scaling signal.
- Confirms this is THE reference baseline "rule-based reactive allocator": threshold/ratio-based control loop + damping window, no look-ahead.

### 2. Knative Pod Autoscaler (KPA) "panic mode" — docs, production
URL: https://knative.dev/docs/serving/autoscaling/kpa-specific/ (accessed 2026-10-04)
- Two modes, **stable** and **panic**, each with its own aggregation window over historical concurrency/RPS metrics: "Stable mode is used for general operation, while panic mode by default has a much shorter window, and will be used to quickly scale a revision up if a burst of traffic arrives."
- Panic window is defined relative to stable window: default `panic-window-percentage` = **10.0** (panic window = 6s when stable-window default is 60s).
- Panic mode trigger: `panic-threshold-percentage` default **200.0** — "panic mode will be started if traffic is twice as high as the current replica population can handle."
- Anti-churn guard while panicking: "When using panic mode, the Revision will not scale down to avoid churn. The Autoscaler will leave panic mode if there has been no reason to react quickly during the stable window timeframe."
- Scale rate asymmetry is explicit policy, not inferred: `max-scale-up-rate` default **1000.0** (can go N→1000N in one cycle) vs `max-scale-down-rate` default **2.0** (N→N/2 max) — i.e., shock absorption is handled by letting scale-up be nearly unbounded while deliberately rate-limiting scale-down.
- This is a second, more sophisticated reactive design than raw HPA: a dual-timescale detector (fast window vs slow window) functions as a crude "change/shock detector" gating a more aggressive response mode — directly relevant to the hackathon's "change-detector" component, though still not predictive/look-ahead.

### 3. AWS EC2 Auto Scaling — Predictive Scaling — docs, production
URL: https://docs.aws.amazon.com/autoscaling/ec2/userguide/predictive-scaling-policy-overview.html (accessed 2026-10-04); overview page: https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-predictive-scaling.html
- "predictive scaling starts analyzing metric data from up to the past **14 days** to identify patterns. It uses this analysis to generate an **hourly forecast of capacity requirements for the next 48 hours**. The forecast is **updated every 6 hours** using the latest CloudWatch data." Needs "at least **24 hours** of data" before it can start forecasting.
- Explicitly framed as look-ahead vs reactive: "Predictive scaling can help you scale faster by launching capacity in advance of forecasted load, compared to using only dynamic scaling, which is **reactive in nature**."
- Ships a **forecast-only mode** first (generate forecasts, don't act) so operators can validate accuracy via `GetPredictiveScalingForecast` before flipping to **forecast-and-scale** mode — a safe-rollout pattern.
- Critical asymmetry (shock-handling design): "If the forecast expects an increase in load, Amazon EC2 Auto Scaling will increase capacity by scaling out. If the forecast expects a decrease in load, **it will not scale in** to remove capacity. If you want to remove capacity that is no longer needed, you must create **dynamic scaling policies**." → production pattern is explicitly: **predictive scale-out + reactive scale-in**, i.e. forecasting is only trusted to add capacity ahead of time; removing capacity (and handling any demand the forecast got wrong) is left to a reactive rule-based guardrail layer running concurrently.
- `SchedulingBufferTime` lets instances pre-launch ahead of the forecasted hour to absorb boot/warm-up latency; "default instance warmup" then blocks scale-in immediately after a scale-out so new capacity isn't thrashed.
- Scaling decisions are applied "at the start of each hour based on the forecast for that hour" — a rolling-horizon forecast re-applied on a fixed cadence, structurally similar to a receding-horizon / MPC-style planner but with a 1-hour decision granularity.

### 4. Azure Monitor — Predictive Autoscale for VM Scale Sets — docs, production
URL: https://learn.microsoft.com/en-us/azure/azure-monitor/autoscale/autoscale-predictive (accessed 2026-10-04)
- "Predictive autoscale uses **machine learning** to help manage and scale Azure Virtual Machine Scale Sets with cyclical workload patterns. It forecasts the overall CPU load... based on your historical CPU usage patterns."
- Data requirements: "needs a **minimum of seven days** of history to provide predictions. The maximum sampling period is a **rolling window of 15 days**." For monthly/yearly seasonality it explicitly tells users to fall back to schedule-based or metric-based (i.e. non-ML) autoscale instead — an acknowledgment of the model's limited horizon/seasonality scope.
- Pre-provisioning window is configurable: "prelaunch instances between **5 and 60 minutes** before the needed prediction time."
- **Identical hybrid pattern to AWS**, stated even more strongly as a hard dependency: "**Predictive autoscale supports scale-out only. Configure standard autoscale to manage to scale in actions.**" and "Before you can enable predictive autoscale or forecast-only mode, **you must set up the standard reactive autoscale conditions**." I.e. Azure will not let you enable the predictive layer at all unless the reactive rule-based layer already exists underneath it — strong evidence this "predictive scale-out on top of mandatory reactive guardrail" is the industry-standard production pattern, not an AWS-specific choice.
- Ships a forecast-only mode identical in purpose to AWS's, plus a 3-chart diagnostic view (actual vs. predicted CPU over last-7-days-to-next-24h, max instance count, current utilization) for operators to build trust before enabling action.
- Narrow metric scope in practice: only supports **Percentage CPU / Average** as the forecast input metric, VMSS only, Commercial cloud only.

### 5. NVIDIA Dynamo Planner — official NVIDIA developer blog, production (v0.2, announced GTC 2025)
URL: https://developer.nvidia.com/blog/nvidia-dynamo-adds-gpu-autoscaling-kubernetes-automation-and-networking-optimizations/ (accessed 2026-10-04)
- Explicitly rejects naive reactive metrics for this domain: "Traditional autoscaling relies on straightforward metrics like queries per second (QPS). However... QPS alone is a poor predictor of system load" for disaggregated LLM serving because "[a] single request with a long input sequence length (ISL) can consume significantly more resources than multiple requests with short ISLs."
- **How Dynamo Planner works** (quoted structure from blog): "Monitors the average KV block utilization across all decode GPUs. Tracks the volume of pending prefill requests in the global prefill queue. Compares these values against **heuristic thresholds, which developers can manually define** during deployment setup. Automatically rebalances resources—either shifting GPUs between prefill and decode phases or provisioning new GPUs from a shared pool."
- Despite the name "Planner," v0.2 is **still a reactive/threshold controller** (manually-set thresholds on current queue/KV-cache state), not a forecasting system — important nuance for the hackathon write-up since "Planner" branding could be mistaken for look-ahead/MPC.
- Designed to run **alongside** Kubernetes autoscaling (HPA) rather than replace it — another data point for "reactive guardrail + specialized domain-aware layer" being the standard composition pattern.
- NOTE: a forum post title ("Dynamo 0.4 Delivers 4x Faster Performance, SLO-Based Autoscaling, and Real-Time Observability", forums.developer.nvidia.com) suggests a later version adds SLO-based (latency/throughput target) autoscaling — **not opened this session, flagged under UNVERIFIED leads** since I did not fetch forums.developer.nvidia.com directly.

### 6. AIBrix (ByteDance / vLLM project) — official readthedocs, production + open-source (docs reflect a recent/active version, 2025)
URLs: https://aibrix.readthedocs.io/latest/features/autoscaling/autoscaling.html and https://aibrix.readthedocs.io/latest/features/autoscaling/predictive-autoscaling.html (accessed 2026-10-04)
- AIBrix ships a `PodAutoscaler` CRD (`autoscaling.aibrix.ai/v1alpha1`) with **three selectable algorithms** plus a separate predictive add-on and an offline optimizer:
  - `HPA` — "Same algorithm as the Kubernetes HorizontalPodAutoscaler." (reactive)
  - `KPA` — "Knative-style: a long stable window plus a short panic window that scales up fast... Metrics are fetched by AIBrix directly rather than through Prometheus, which shortens reaction time." (reactive, dual-window, same panic-mode concept as Knative above but with a faster metrics path)
  - `APA` — "AIBrix's own algorithm. Like HPA but with a **fluctuation tolerance that must be exceeded before any scaling happens**, which suppresses oscillation." (reactive with hysteresis/deadband, explicitly for anti-thrash)
  - Optimizer-based — "computes the replica count from **offline benchmark profiles and an SLO**" for heterogeneous-GPU cost optimization (static/offline optimization, not online forecasting)
- **Predictive Autoscaling (opt-in, `spec.predictive`)** is the most directly relevant primary-source evidence for "look-ahead vs reactive" framing in this whole research set — AIBrix's own docs state the rationale explicitly: "Reactive autoscaling waits for the metric to move before it adds replicas, which costs at least **one pod start-up time of headroom**. Predictive autoscaling closes part of that gap: it **projects the metric trend of the observation window forward** and, in `Auto` mode, uses the projection as a **floor** for scale-up. **The reactive decision is never replaced, and a projection never scales a workload down.**"
- Mechanism: linear trend fit over `observeWindowSeconds`, projected to `now + horizonSeconds`; example config uses `horizonSeconds: 120` over `observeWindowSeconds: 180`. Auto mode: `final = max(reactive, projected)`. Preview mode: compute + record only, no action (same safe-rollout idea as AWS/Azure forecast-only).
- **Important caveat, quoted exactly**: "The feature is opt-in through `spec.predictive`... Today the block is accepted and validated only: applying it writes no `status.predictive` and changes no replica count. **The controller that consumes these fields lands in a follow-up.**" → at the time these docs were written, predictive autoscaling in AIBrix is a **designed-but-not-yet-active** feature (schema/validation shipped, execution logic pending) — a valuable, nuanced finding: even a 2025 LLM-serving-focused project explicitly separates "predictive signal" from "trusted actuation," and the trusted actuation path isn't live yet.
- Limitation stated: "Predictive scaling is **not supported with `scalingStrategy: HPA`**. The HPA strategy delegates the decision to a native `HorizontalPodAutoscaler` resource, which has no channel to receive the projection, so the combination is rejected by the validating webhook." Reinforces that look-ahead is bolted on as a floor onto a reactive core, architecturally coupled to AIBrix's own reactive algorithms (KPA/APA), not a replacement for them.

### 7. Uber Engineering — "Enhancing Uber's Guidance Heatmap with Deep Probabilistic Models" — official engineering blog, production
URL: https://www.uber.com/us/en/blog/enhancing-ubers-guidance-heatmap-with-deep-probabilistic-models/ (accessed 2026-10-04)
- This is a **demand-side guidance/nudge system**, not a hard dispatch/assignment engine: "our AI team has developed probabilistic prediction models that power guidance tools like the Heatmap... giving drivers information for making decisions about when and where to drive." Reallocation of supply happens because drivers choose to reposition themselves in response to the forecast, not because Uber directly commands vehicle movement — an important alternative pattern vs. direct fleet/robot reallocation (demand-shaping via information/incentive rather than direct control).
- "The heatmap **updates every 10 minutes**, ensuring drivers receive up-to-date estimates highlighting areas forecasted to have above-average earnings opportunities." Model target is **earnings per hour (EpH)** specifically chosen "to account for real time fluctuations in rider demand, surge pricing, and holiday seasonality."
- Model evolution (explicit progression, each step motivated by a real limitation): "The first version... used **XGBoost** to predict mean EpH with mean squared error (MSE) loss" → single-Gaussian NLL deep net ("mean and standard deviation output by the model can be thought of as parameterizing the entire predicted distribution of earnings over the next hour") → **Gaussian Mixture Model (GMM)** because "the typical distribution of individual EpH at a hex-time exhibits multiple peaks, which goes against our original assumption of a Gaussian distribution with a single peak." Directly evidences production ML practice moving from point-forecasts to full predictive distributions to better inform downstream (human or automated) allocation decisions.
- Operates at **Hex-9 granularity** using Uber's H3 geospatial indexing system — a concrete precedent for spatial discretization choice in a resource-reallocation system design.

### 8. Lyft — "A Better Match for Drivers and Riders: Reinforcement Learning at Lyft" — arXiv preprint (Lyft-authored), maturity: paper, production-deployed
URL: https://arxiv.org/abs/2310.13810 (accessed 2026-10-04, abstract read via page metadata)
- Exact abstract quote: "To better match drivers to riders in our ridesharing application, we revised Lyft's core matching algorithm. We use a **novel online reinforcement learning approach that estimates the future earnings of drivers in real time** and use this information to find more efficient matches. This change was **the first documented implementation of a ridesharing matching algorithm that can learn and improve in real time**."
- This is categorically different from the autoscaling examples above: RL is applied directly to the **hard assignment problem** (which driver is matched to which rider), using an estimate of *future* earnings (a value-function-like look-ahead) as the signal that shapes the current match — i.e. look-ahead is baked into the per-decision objective, not bolted on as a separate forecast-then-cap layer.
- Validation method: "evaluated the new approach during **weeks of switchback experimentation** in most Lyft markets" (switchback = randomize treatment by time-window within each market, standard for marketplace experiments where you can't cleanly A/B individual rides).
- Reported numbers (exact quote): "it enabled our drivers to serve **millions of additional riders** each year, leading to **more than $30 million per year in incremental revenue**. Lyft rolled out the algorithm globally **in 2021**."
- Gap: the abstract (the only part read this session — full paper not fetched due to PDF/HTML fetch failures) does not describe explicit shock-handling or drift-adaptation mechanics; "learn and improve in real time" is the only textual evidence of continual/online adaptation. ### 9. DoorDash Engineering — "Using ML and Optimization to Solve DoorDash's Dispatch Problem" (orig. 2021-08-17) — official engineering blog, production
URL (live, 403 at fetch time): https://doordash.engineering/2021/08/17/using-ml-and-optimization-to-solve-doordashs-dispatch-problem/ → resolved/read via web.archive.org snapshot: https://web.archive.org/web/20241128221154/https://careersatdoordash.com/blog/using-ml-and-optimization-to-solve-doordashs-dispatch-problem/ (accessed 2026-10-04)
- Names the production system directly: "**DeepRed**, the system at the center of our last-mile logistics platform... how to get each order from the store to the customer, via Dashers, as efficiently as possible."
- **Two-stage architecture, quoted**: "the dispatch engine is built on two sets of mathematical models. The first set of models are **ML models** that are trained to estimate how an order will unfold if we offer it to a particular Dasher... Once the estimates are made they are fed into our second modeling layer, our **mixed-integer optimization model**. The optimization model makes the final recommendations about which orders to offer to which Dashers." — a textbook **predict-then-optimize** pipeline (ML prediction layer feeding a combinatorial assignment/optimization layer), structurally analogous to a "forecaster + assignment solver" design.
- Explicit external shock factors named: "weather and traffic that can impact delivery times or cause Dashers to refuse orders at higher rates... if it's raining and many Dashers use motorbikes we can expect fewer accepted deliveries, which can cause lateness."
- Undersupply/shock handling is an **optimization trade-off, not a separate panic mode**: "there may be times when we don't have enough Dashers to pick up all the orders. In these undersupply scenarios, we have to make tradeoffs about which orders to pick up now versus later" plus order-batching (one Dasher, multiple nearby orders) to raise effective throughput per Dasher.
- Continuous improvement loop: "The second stage was to build **simulation and experimentation platforms** that would allow us to make continual improvements to our dispatch service" — i.e. offline simulation is the validation methodology before changes reach the live marketplace, directly relevant to how a hackathon team might validate a planner against historical demand traces before claiming it "beats" a baseline.
- Gap: this specific post (2021) describes real-time assignment optimization, not an explicit multi-period demand *forecast* driving pre-positioning; a separate, not-opened post ("Next-Generation Optimization for Dasher Dispatch at DoorDash", 2020, linked from within this post) likely has earlier architecture detail — **UNVERIFIED lead**, not fetched this session.
