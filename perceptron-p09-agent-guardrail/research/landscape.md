## 1. The crux, in one paragraph
A hallucinated action is usually **well-formed**: a real tool, valid JSON and plausible values, with one value that no source supports. Examples are an invented ticker, a quantity ×10, the wrong account, a limit price the user never gave, or a fee the policy doesn't state. Schema checks pass these by construction. The 2026 closed-world-resolution study says the same thing from the other side. Registry and signature checks leave an "irreducible residue (borrowed arguments schema-indistinguishable from a valid call)" ([2609.19425](https://arxiv.org/abs/2609.19425)). Catching that residue needs **argument-level grounding**: where did this value come from, and does a trusted source agree? It also needs a policy for **absence of evidence**, which is different from contradiction. All of this costs **latency**, and every false block costs **utility**. "Stale Does Not Mean Unsafe" shows that coarse guards can block 92–95% of benign cases while precise semantic predicates block none ([2609.29522](https://arxiv.org/abs/2609.29522)).

**Taxonomy of approaches.** (a) *Input/content classifiers*: PromptGuard, Llama Guard, Model Armor. (b) *Intent/alignment monitors* on reasoning or trajectories: AlignmentCheck, AI-control monitors, ShieldAgent. (c) *Policy engines and DSLs* over tool calls: AgentSpec, Progent, ActGov, AgentFlow, Invariant, Cedar. (d) *Architectural isolation*: CaMeL, design patterns. (e) *Structural resolution*: closed-world registry/signature. (f) *Simulation and undo*: ToolEmu, GoEx. (g) *Learned sentinels*: Safiron, HiSentinel.

**What is not solved (our opening).** (1) **Argument values vs a knowledge source.** Policy engines check what you write as a rule. Resolvers check the schema. Nobody routinely asks where each value came from and whether a trusted source supports it. (2) **Absence vs contradiction.** Most systems output allow/deny and have no third state for "unverifiable → ask". (3) **A calibrated cost frontier.** The false-block/miss trade-off is formalised (2607.22868) but rarely reported next to latency. (4) **Checker hallucination.** LLM judges can approve invented values; few systems verify the judge's own evidence. (5) **Domain stakes.** None of the opened work targets trading or finance operations, where the pre-trade-control discipline already exists (§6).

## 3. Verifier models for a laptop (fast tier vs careful tier)
From model cards opened by the verifier-models agent ([notes/verifier-models.md](notes/verifier-models.md)):
- **Fast tier.** `vectara/hallucination_evaluation_model` (HHEM-2.1-Open, Apache-2.0, premise/hypothesis scorer) or `cross-encoder/nli-deberta-v3-small` (3-way NLI). Both are classification heads, not generators, so they are the realistic sub-50 ms candidates. Laptop latency is **UNVERIFIED** until we measure it.
- **Careful tier.** `ibm-granite/granite-guardian-3.2-5b` is the only guard model whose card names a **"Function Calling Hallucination"** risk, alongside groundedness and context relevance. IBM's page says Granite Guardian has stayed "in the top 3 on the LLM-Aggrefact Leaderboard (as of 10/2/2025)". `gpt-oss-safeguard` takes bring-your-own-policy text.
- **Our skeleton tonight** uses only local models already on disk: Qwen3-1.7B-4bit (fast) and Qwen3-8B-4bit (careful) via MLX. Measured on this M5: about 1.8 s and 2.7 s for an 8-token generation, without prompt caching (see thought node log).

**Pattern.** Industry ships (1) **hooks** (custom code sees arguments), (2) **classifiers** on prompts and responses, (3) **declarative policy gates** (Cedar, Invariant), and (4) **human confirmation**. Grounding products (Vertex check-grounding, Azure groundedness, Bedrock contextual grounding) check **response text**, not **action arguments**. None of the opened docs ships *argument-level provenance against a reference KB with a third "unverifiable" state and risk-routed escalation*. That is where we build.

## 6. The finance analogue: pre-trade risk controls (Optiver's home turf)
SEC Rule 15c3-5 requires broker-dealers with market access to "prevent the entry of erroneous orders, by rejecting orders that exceed appropriate price or size parameters… or that indicate duplicative orders". It also requires them to prevent orders that "exceed appropriate pre-set credit or capital thresholds" and orders "for securities for a… customer… restricted from trading those securities" (verbatim, [notes/pretrade-risk-controls.md](notes/pretrade-risk-controls.md)). Trading has run **deterministic checks before execution, sized by risk**, for over a decade. Our checker maps each control to an agent-action check (price collar → limit-price bounds from reference data; duplicative orders → idempotency; restricted list → entity denylist; credit thresholds → cash and notional limits). It then adds the piece trading does not need: **provenance of intent**, because an agent, unlike a trader, can invent the order itself. RTS 6 Art. 15 and the Knight Capital order are UNVERIFIED until opened.

## 8. Implications for our design
1. Make **argument provenance** the core check. Each intent-bearing argument must trace to the user's words, the KB or trusted tool data. Untrusted text is never a source of intent (CaMeL/IFC spirit, implemented as a per-argument check).
2. Use **three-way verdicts** (pass / fail / unverifiable) and route unverifiable to a model or a human by risk (AI-control pattern; Ctrl-Z numbers show the safety/usefulness trade-off is real).
3. Run **deterministic pre-trade-style contracts first** (µs–ms). Use LLMs only for the residue, and let an LLM verdict count only if its quoted evidence is found verbatim in the source.
4. Report the **frontier, not a point**: catch rate, false-block rate, escalation rate and latency, on held-out phrasings and on real model errors (τ-bench replay), with calibrated thresholds (conformal / Learn-then-Test; see [notes/routing-control-cascades.md](notes/routing-control-cascades.md)).
